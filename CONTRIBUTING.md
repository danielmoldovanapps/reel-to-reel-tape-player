# Contributing

Daniel Moldovan ([RO]Daniel) owns and manages the upstream project and its
releases. Start with a fork and propose changes through pull requests. No
upstream write or administrator access is needed for that workflow.

## Initial packaging contributions

Keep packaging work separate from application behaviour changes. Explain the
reason for every new dependency, permission, download source, or executable
build step. Pin release sources and verify checksums where appropriate.

Do not change donation destinations, branding, copyright notices, or licensing
as an incidental packaging change. Any proposed change to those areas must be
explicitly identified and reviewed by the project owner. Contributions must
respect the existing first-party and third-party licenses.

Include build and test results and disclose limitations. A successful build or
static check is not evidence that sound output, portals, file selection,
settings persistence, or winding effects work on a desktop.

## Flatpak / Flathub

Flathub packaging is a separate contribution. Under the Flathub policy checked
on October 21, 2026, manifests must not contain AI-generated or AI-assisted
content, and submission/review text must not be generated by AI agents.
A human packager must independently write the manifest and handle the submission
and review interactions. Do not copy or lightly rewrite an AI-generated manifest
and represent it as independently human-written.

Review AI-ASSISTANCE.md and disclose the application development history and the
scope of generated material to reviewers as required. The project owner should
be involved in the submission and retain access to the resulting packaging
repository. Discuss ongoing maintenance, update approval, and release access
before anyone submits the app. Nobody is authorized by this document alone to
publish an official release or claim to be the project's owner.

Current policies: https://docs.flathub.org/docs/for-app-authors/requirements

## Application changes

Explain the user-visible problem and how the change addresses it. Keep unrelated
changes separate. Preserve existing playback, transport, branding and playlist
behaviour unless the project owner explicitly agrees to change it.

Useful checks include Python/JavaScript syntax, source/package consistency,
Debian package inspection, and desktop playback tests. Existing scripts under
tests/ were written during earlier browser-based development. They require
Playwright, Chromium and FFmpeg, contain historical timing expectations, and
are not a substitute for testing the current WebKitGTK desktop application.

## Review and access

The project owner decides which proposals to accept. Start with no collaborator
write access. Any later access or shared publishing arrangement requires a
separate explicit decision by the project owner. Do not ask for passwords,
private SSH keys, recovery codes, or personal publishing tokens.

These written guidelines do not enforce GitHub permissions. The owner must
configure repository access and branch protection separately.
